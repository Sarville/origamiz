## Dev server access

`npm run gulp` (default task) serves the standalone dev build via browser-sync
on port 3005. Don't hand the user a raw `http://<hostname>.<tailnet>.ts.net:3005/`
link — confirmed unreliable from at least one real phone (large transfers like
the JS bundle stall/drop, only works via a Tailscale exit node). Instead run
`tailscale serve --bg --https=<port> 3005` and give that URL — it routes
through tailscaled's own HTTPS proxy and reliably reaches devices without an
exit node. Check `tailscale serve status` first for already-used ports/URLs
(other services on this machine use this pattern too).

**Building-platform margin (the "buildings bigger than tiles" bug) — final,
correct rule, don't reopen without rereading §5–§7 of that session file:**
the true playable grid cell is 174×174px *per tile*, not the 192px sprite
canvas size. Every procedurally-generated building's platform must stay
inset from its own canvas edge by `margin_per_side = (canvas_dim_px // 192)
* 9`, computed independently per axis (`_mg(dim)` in `build_batch.py`/
`build_platform.py`) — so a 1-tile axis gets 9px, a 2-tile axis gets 18px.
This applies to **every side, including belt connections** — two earlier
attempts this session got that part wrong (first: margin nowhere, then:
margin only on free sides, connections reaching the true edge) before the
user proved via pixel measurement that connections need the same margin
too. The only thing allowed to cross into the margin is the direction
arrow. Wires-layer-only buildings (photoreal AI art) and `hub.png` are
explicitly exempt — different convention, not built by this engine.

Source art for the buildings/blueprints/toolbar/wires work lives in

**Bigger gotcha: any `res_raw/**` sprite change needs a manual JS rebuild too.**
`src/js/core/atlas_definitions.js` statically imports
`../../../res_built/atlas/*.json` (the packed-atlas coordinate map) — the
bundler inlines that data into the JS bundle at build time
(`res_built_atlas_atlas0_{hq,mq,lq}_atlas.bundle.js` chunks). The dev
server's watcher chain (`res_raw/**/*.png` → `imgres.buildAtlas` →
`imgres.atlasToJson` → `imgres.atlas`) only regenerates the atlas PNG/JSON
on disk; nothing watches `res_built/atlas/*.json` to trigger
`js.standalone.dev.build`. Result: after swapping any building/belt/wire
sprite, the served atlas **texture** is fresh but the running JS bundle's
baked-in **coordinates** into that texture are stale — every sprite can
render as the wrong crop/region, looking like total breakage across all
buildings and belts at once, while the atlas PNG itself (inspect it
directly) looks perfectly fine. Confirmed and fixed for real 2026-08-28,
see `sessions/2026-08-28-0923-session.md`. **After any `res_raw/**` sprite
swap, always run, in order:** `npx gulp --cwd gulp imgres.buildAtlas`,
`imgres.atlasToJson`, `imgres.atlas`, then `js.standalone.dev.build` — then
hard-refresh the browser (a normal reload can still serve a cached bundle).

**If `imgres.atlasToJson` throws `Cannot read properties of undefined
(reading 'split')`** (found 2026-08-28): the "hq" atlas has overflowed a
single 2048x2048 texture page (`atlas2json.js` only supports one page,
comment says so) - check `res_built/atlas/atlas0_hq.atlas` for more than
one `atlas0_hq*.png` page header. Fix: bump `res_raw/atlas.json`'s
`maxWidth` (and/or `maxHeight`) up a power of two - taken from 2048 to
4096 that session, back to one page. Don't waste time treating this as a
flaky/transient Java issue — it repros deterministically once the atlas
is actually over budget, re-running `buildAtlas` alone won't fix it.

**Gotcha when swapping `res/ui/**` files:** most of that tree is a plain
static-file copy with no rebuild step, but `building_icons` (and anything
else `src/css/*.scss` references via `uiResource()`/`inline()`, e.g.
`resources.scss`'s `$buildings`/`$buildingsAndVariants` lists) gets
base64-embedded into compiled CSS at build time — the dev server's watcher
only recompiles CSS on a `.scss` change, not on a change to a PNG an
`inline()` call references. After swapping such a file, `touch
src/css/resources.scss` (or run `npx gulp --cwd gulp css.dev`) to force the
re-embed, then hard-refresh the browser. See
`sessions/2026-08-28-0109-session.md` for the full diagnosis (a real
gotcha, not a caching bug — don't re-chase it as one).

**`gulp/preloader/preloader.css` is not in any watch glob** (found
2026-08-31) — `gulp/tasks.js` only watches `../src/html/**` for the `html`
task that inlines this file's contents into `index.html`'s `<head>`, so
editing `preloader.css` alone never triggers a rebuild, no matter how long
you wait. A full kill+restart of the `npm run gulp` process (not just a
partial task re-run) is the fix, same as other stale-watcher gotchas above —
confirm via `grep` on `build/main.css`/the served HTML, not just eyeballing
a screenshot.

## Mobile UI gotchas (found 2026-08-30, see `sessions/2026-08-30-2156-session.md`)

**Every `StyleBelowWidth`/`.is-mobile` media query was dead on real phones
until 2026-08-30** because `src/html/index.html` had no
`<meta name="viewport">` tag at all — browsers default to a ~980px layout
viewport without one, so no mobile CSS could ever match regardless of how
correct it was. Now fixed, but if a mobile style ever appears to have "no
effect" again on a real device, check `window.innerWidth` and
`matchMedia(...).matches` first before assuming the CSS itself is wrong.

**Every element is `pointer-events: none` by default** (the `* {...}` rule
in `common.scss`) — anything meant to be tappable must explicitly opt back
in with `pointer-events: all`, and that does NOT cascade automatically to
children of an element that already opted in. A real bug (building-preview
sprite tap-to-rotate silently doing nothing) traced to exactly this: the
parent had `pointer-events: all`, an inner wrapper didn't. When a tap/click
"does nothing" on an otherwise-correctly-wired element, check computed
`pointer-events` via `getComputedStyle`/`document.elementFromPoint()`
before assuming the JS listener itself is broken.

**Testing tap/click via `element.dispatchEvent(new TouchEvent(...))` gives
false positives** — it bypasses hit-testing/`pointer-events` entirely. Only
CDP's `Input.dispatchTouchEvent`/`dispatchMouseEvent` at real screen
coordinates (or an actual device) exercises the real path.

**Stacking order for HUD/dialog elements is controlled by the `$elements`
list in `src/css/main.scss`**, not by ad-hoc `z-index` values in a
component's own stylesheet — it assigns each listed ID an incrementing
`z-index` (starting at 100, +10 per entry) by list position. An element
with its own hardcoded `z-index` outside that list can end up on the wrong
side of a dialog. Also: **an ID selector always beats a class selector**
regardless of source order or value, so a class-level override like
`.ingameDialog { z-index: 10000; }` is silently inert against any dialog
(they're all matched by their own `#id` in the registry) — the only real
fix is adding/reordering the element's ID within `$elements` itself.

## Belt auto-routing (item 9) gotchas, found 2026-08-31 in `mobile_controls.js`

**`GameLogic.getEjectorsAndAcceptorsAtTile` (`src/js/game/logic.js`) is the
authoritative source for ejector/acceptor local→world tile+direction math** —
if any future code needs to compute "what tile/direction feeds a building's
acceptor slot" or "what tile/direction a building's ejector slot launches
into" without an actual neighboring entity to query it live, derive it by
re-reading that function's math directly, not by intuition. Got it backwards
once already (subtracted a direction vector instead of adding it, used a
slot's own direction instead of its inverse) — silently planned a feed tile
on the wrong side of the building. Caught only by cross-referencing this
function and independently re-confirming via
`MetaBeltBuilding.computeOptimalDirectionAndRotationVariantAtTile`.

**To bypass a locked/not-yet-clickable toolbar building in a CDP test
script**, use `root.hud.parts.buildingsToolbar.buildingHandles['<id>'].metaBuilding`
directly with `mc.placerLogic.currentMetaBuilding.set(...)` — tapping a
locked toolbar icon does nothing (no error, just silently fails), which
looks identical to a mistaken selector/coordinates at first.

**The auto-tunnel/routing engine (`findBeltPath`/`placePath`/etc.) lives in
`hud/parts/belt_path_planner.js` as a standalone `BeltPathPlanner` class**
since 2026-09-01 — it used to live directly on `HUDMobileControls`
(`mobile_controls.js`), which still uses it (via `this.beltPathPlanner`,
threading its own `lastBeltTile`/`lastBeltIncomingDirection` continuation
state through as explicit params on every call), but so does desktop's
`HUDBuildingPlacerLogic` (`building_placer_logic.js`) for its belt drag —
check there first before assuming a routing bug is mobile-only or
re-deriving pathfinding logic that already exists. Fixes to it (e.g. the
2026-09-01 opportunistic-connection and anti-stranding `forcedExitDirection`
work) apply to both platforms automatically since they share the class,
just each HUD part holds its own instance.

**Placement while zoomed out into map overview (`root.camera.getIsMapOverlayActive()`)
is gated in three independent, easy-to-miss places, not one** — found
2026-09-01 building mobile support for it (2c-7 in `TODO.md`): `HUDMobileControls.onMouseDown`'s
entry guard, `HUDBuildingPlacerLogic.tryPlaceCurrentBuildingAt` (also the
path a blueprint's confirm button and a belt's very first tap take), and
`HUDBuildingPlacerLogic.update()`'s per-tick "deselect while in overview"
housekeeping — that third one is the sneaky one, since it fires every
frame and will quietly re-clear a selection that only the *first* guard was
relaxed for, making it look like the relaxation "didn't take" a moment
later. All three now consult one shared `hud/parts/overview_building.js`
(`OverviewBuildingPolicy.isAllowed()`), gated behind `IS_MOBILE` so desktop
is untouched — **2c-8 (desktop's own belt click while zoomed out, not
started) will need the same three call sites relaxed again, minus the
`IS_MOBILE` guard**, plus checking desktop's separate onMouseDown/onMouseMove/
onMouseUp in `building_placer_logic.js` for their own overview blocks (not
yet touched at all, since desktop was explicitly out of scope this round).

**`window.globalRoot` is the live `GameRoot` instance, exposed globally once
in-game** (`core.js`) — the fastest way to inspect/drive real game state
from a CDP `Runtime.evaluate` call (map contents via
`globalRoot.map.getLayerContentXY(x, y, "regular")`, current placement
state via `globalRoot.hud.parts.buildingPlacer`/`.mobileControls`, hub
goals, etc.) instead of guessing from screenshots. Combine with
`root.camera.center`/`.zoomLevel`/`root.gameWidth`/`root.gameHeight` (tile
size is `globalConfig.tileSize`, currently 32) to convert a tile coordinate
to a screen point for real `Input.dispatchMouseEvent`/
`Input.dispatchTouchEvent` calls: `screenX = (tileX*32+16 - centerX)*zoom +
gameWidth/2` (same for Y) — this is `Camera.worldToScreen`'s own formula,
duplicated in JS since it needs a real `Vector` instance to call as a
method.

**`src/js/core/config.local.js` is gitignored, but editing it is NOT
side-effect-free** — it's baked into the one gulp-served JS bundle, so
toggling a flag live-reloads (and resets to the main menu) *every* browser
tab currently pointed at the dev server, including the user's own, not just
your own disposable CDP Chrome instance. Confirmed live 2026-09-01: the user
was mid-session on their phone when a `fastGameEnter`/`rewardsInstant`/
`allBuildingsUnlocked` toggle for CDP testing kicked their tab back to the
main menu. `fastGameEnter: true` skips the main menu straight into a game,
`rewardsInstant: true` + `allBuildingsUnlocked: true` unlocks everything
(including tunnels, gated separately behind `hubGoals.isRewardUnlocked` —
note `allBuildingsUnlocked` alone already makes that check always return
true, see `hub_goals.js`), `instantMiners: true` makes extractors produce
immediately for item-flow testing. **Prefer navigating the real menu (New
Game) or resuming a disposable savegame in your own CDP tab instead** —
reserve editing this file for when you're confident no one else has the dev
server open, and always revert it to fully-commented before finishing
either way (diff against a fresh `git show HEAD:...` won't work since it's
untracked, but every line is `// key: true,` by default so reverting is
just re-commenting whatever was enabled).

## `ActionHistory` (undo/redo) transaction gotcha, found 2026-09-01

**`GameLogic.tryDeleteBuilding`/`tryPlaceBuilding` only become undoable
inside an open `actionHistory.beginTransaction()`/`endTransaction()`
pair** — they unconditionally call `actionHistory.noteEntityWillBeDeleted`/
`noteEntityPlaced`, but both are silent no-ops when no transaction is open
(see `action_history.js`'s class doc). Calling either without the wrap
still changes the map, but a later `actionHistory.undo()` either does
nothing or undoes some unrelated earlier action — not the change you just
made. Bit `mobile_controls.js`'s long-press-to-move-a-building rewrite
this session exactly this way (cancel silently failed to restore the
picked-up building) after a refactor dropped the wrap the original code
had. Desktop's own mouse place/delete path (`building_placer_logic.js`)
has never wrapped either call in a transaction at all — its placements/
deletions are invisible to undo/redo entirely; not touched this session,
out of scope, but don't assume desktop undo covers them if that's ever
revisited.

**`ActionHistory.combineLastTwo()`** (added this session) collapses the
two most recent undo-stack entries into one — used so confirming a
long-press building move (a delete transaction pushed at pickup time, a
placement transaction pushed at confirm time) undoes as a single step
straight back to the original tile, not two.

**Mobile's long-press-on-an-existing-building pickup goes through the
*same* toolbar-select ghost flow as tapping its icon** (`currentMetaBuilding`/
`blueprintTile` in `HUDMobileControls.beginMoveExistingBuilding`/
`drawBlueprintGhost`), not the copied-blueprint mechanism
(`blueprintPlacer.currentBlueprint`/`copiedBlueprintTile`) — that one is
now select-mode multi-copy only (`onCopyClicked`). They look superficially
similar (both show a finger-follow ghost with a confirm/rotate/cancel
row) but the copied-blueprint one shows a cost tag and deliberately never
exits placement mode on confirm (correct for "paste this clipboard
blueprint again"), which is wrong for "move one building" — don't merge
them back without re-reading this distinction.

## Testing the game visually in this sandbox

Headless Chrome (`--headless --screenshot=...`) reports `document.hidden = true`,
and the game itself pauses boot/rendering when hidden — this looks like a hang
but isn't a bug. For a real visual check, use Xvfb + non-headless Chrome +
`import -window <id>` (ImageMagick) for the screenshot instead.

To inspect a HUD element directly instead of guessing from a screenshot
(what it actually is, its class list, its real on-screen rect), launch
Chrome with `--remote-debugging-port=<N> --remote-allow-origins=*` and run
`Runtime.evaluate` over its CDP websocket (Node 22+'s built-in
`WebSocket` is enough, no npm install needed). Cheap and saved real time
once (2026-08-28): a wood-plank toolbar row was mistaken for an in-world
conveyor belt in several screenshots — `getBoundingClientRect()` on
`.ingame_buildingsToolbar` settled it in one call instead of more
tutorial-mashing to "reach" the UI.

**When opening a fresh CDP tab to verify a CSS/asset change, disable cache
*before* navigating, not after** (found 2026-08-31) — creating a tab via
`PUT /json/new?<url>` starts fetching immediately, racing your WebSocket
connection; calling `Network.setCacheDisabled` after that connects is too
late for that first load and can silently serve a stale stylesheet from
this sandbox's long-lived, reused Chrome debug profile (real symptom: one
element's color updates, a sibling rule from the same stylesheet doesn't —
looks like a partial rebuild bug but isn't). Open `about:blank` first,
connect, call `Network.enable` + `Network.setCacheDisabled: true`, *then*
`Page.navigate`. Cross-check against `build/main.css` on disk (`grep` for
the hex/string in question) if a screenshot ever looks inconsistent within
itself.

**Canvas-drawn HUD elements (hub, etc.) use `globalConfig.tileSize` (32,
a logical-world-unit constant) for their coordinate space, NOT the 192px
building-sprite export size.** E.g. the hub's dynamic text canvas
(`HubSystem.redrawHubBaseTexture` in `src/js/game/systems/hub.js`) is
`4 * tileSize` = **128×128**, not 768×768 — confirmed the hard way
2026-08-28 (first draft assumed 768, a chip meant to be a small corner
badge rendered covering half the hub). If a coordinate in one of these
`redraw*Texture` methods looks tiny (e.g. `27, 32`) relative to what
you'd expect for a "768px" building sprite, that's the tell — it's
already in the small logical space, don't rescale it up.
