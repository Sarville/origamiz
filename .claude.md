## Dev server access

`npm run gulp` (default task) serves the standalone dev build via browser-sync
on port 3005. Don't hand the user a raw `http://<hostname>.<tailnet>.ts.net:3005/`
link — confirmed unreliable from at least one real phone (large transfers like
the JS bundle stall/drop, only works via a Tailscale exit node). Instead run
`tailscale serve --bg --https=<port> 3005` and give that URL — it routes
through tailscaled's own HTTPS proxy and reliably reaches devices without an
exit node. Check `tailscale serve status` first for already-used ports/URLs
(other services on this machine use this pattern too).

**Building-platform margin (the "buildings bigger than tiles" bug) — final,
correct rule, don't reopen without rereading §5–§7 of that session file:**
the true playable grid cell is 174×174px *per tile*, not the 192px sprite
canvas size. Every procedurally-generated building's platform must stay
inset from its own canvas edge by `margin_per_side = (canvas_dim_px // 192)
* 9`, computed independently per axis (`_mg(dim)` in `build_batch.py`/
`build_platform.py`) — so a 1-tile axis gets 9px, a 2-tile axis gets 18px.
This applies to **every side, including belt connections** — two earlier
attempts this session got that part wrong (first: margin nowhere, then:
margin only on free sides, connections reaching the true edge) before the
user proved via pixel measurement that connections need the same margin
too. The only thing allowed to cross into the margin is the direction
arrow. Wires-layer-only buildings (photoreal AI art) and `hub.png` are
explicitly exempt — different convention, not built by this engine.

Source art for the buildings/blueprints/toolbar/wires work lives in
`assets_wip/origamiz_pilot/`. Before touching that pipeline, read
`sessions/2026-08-26-2232-session.md` (AI-generation-era pitfalls: rotation-sign
bugs, `despill.py` destroying the intentionally-green tunnel gates, why belt
corners must be procedural not AI-drawn, why opening width is a measured
constant not a guess) AND `sessions/2026-08-27-1456-session.md` (current
construction algorithm — the AI-drawn hut/frame look from the first session
is now superseded by a fully procedural platform+curb engine in
`build_platform.py`/`build_batch.py`; that file has every measured constant,

**Bigger gotcha: any `res_raw/**` sprite change needs a manual JS rebuild too.**
`src/js/core/atlas_definitions.js` statically imports
`../../../res_built/atlas/*.json` (the packed-atlas coordinate map) — the
bundler inlines that data into the JS bundle at build time
(`res_built_atlas_atlas0_{hq,mq,lq}_atlas.bundle.js` chunks). The dev
server's watcher chain (`res_raw/**/*.png` → `imgres.buildAtlas` →
`imgres.atlasToJson` → `imgres.atlas`) only regenerates the atlas PNG/JSON
on disk; nothing watches `res_built/atlas/*.json` to trigger
`js.standalone.dev.build`. Result: after swapping any building/belt/wire
sprite, the served atlas **texture** is fresh but the running JS bundle's
baked-in **coordinates** into that texture are stale — every sprite can
render as the wrong crop/region, looking like total breakage across all
buildings and belts at once, while the atlas PNG itself (inspect it
directly) looks perfectly fine. Confirmed and fixed for real 2026-08-28,
see `sessions/2026-08-28-0923-session.md`. **After any `res_raw/**` sprite
swap, always run, in order:** `npx gulp --cwd gulp imgres.buildAtlas`,
`imgres.atlasToJson`, `imgres.atlas`, then `js.standalone.dev.build` — then
hard-refresh the browser (a normal reload can still serve a cached bundle).

**If `imgres.atlasToJson` throws `Cannot read properties of undefined
(reading 'split')`** (found 2026-08-28): the "hq" atlas has overflowed a
single 2048x2048 texture page (`atlas2json.js` only supports one page,
comment says so) - check `res_built/atlas/atlas0_hq.atlas` for more than
one `atlas0_hq*.png` page header. Fix: bump `res_raw/atlas.json`'s
`maxWidth` (and/or `maxHeight`) up a power of two - taken from 2048 to
4096 that session, back to one page. Don't waste time treating this as a
flaky/transient Java issue — it repros deterministically once the atlas
is actually over budget, re-running `buildAtlas` alone won't fix it.

**Gotcha when swapping `res/ui/**` files:** most of that tree is a plain
static-file copy with no rebuild step, but `building_icons` (and anything
else `src/css/*.scss` references via `uiResource()`/`inline()`, e.g.
`resources.scss`'s `$buildings`/`$buildingsAndVariants` lists) gets
base64-embedded into compiled CSS at build time — the dev server's watcher
only recompiles CSS on a `.scss` change, not on a change to a PNG an
`inline()` call references. After swapping such a file, `touch
src/css/resources.scss` (or run `npx gulp --cwd gulp css.dev`) to force the
re-embed, then hard-refresh the browser. See
`sessions/2026-08-28-0109-session.md` for the full diagnosis (a real
gotcha, not a caching bug — don't re-chase it as one).

## Testing the game visually in this sandbox

Headless Chrome (`--headless --screenshot=...`) reports `document.hidden = true`,
and the game itself pauses boot/rendering when hidden — this looks like a hang
but isn't a bug. For a real visual check, use Xvfb + non-headless Chrome +
`import -window <id>` (ImageMagick) for the screenshot instead.

To inspect a HUD element directly instead of guessing from a screenshot
(what it actually is, its class list, its real on-screen rect), launch
Chrome with `--remote-debugging-port=<N> --remote-allow-origins=*` and run
`Runtime.evaluate` over its CDP websocket (Node 22+'s built-in
`WebSocket` is enough, no npm install needed). Cheap and saved real time
once (2026-08-28): a wood-plank toolbar row was mistaken for an in-world
conveyor belt in several screenshots — `getBoundingClientRect()` on
`.ingame_buildingsToolbar` settled it in one call instead of more
tutorial-mashing to "reach" the UI.

**Canvas-drawn HUD elements (hub, etc.) use `globalConfig.tileSize` (32,
a logical-world-unit constant) for their coordinate space, NOT the 192px
building-sprite export size.** E.g. the hub's dynamic text canvas
(`HubSystem.redrawHubBaseTexture` in `src/js/game/systems/hub.js`) is
`4 * tileSize` = **128×128**, not 768×768 — confirmed the hard way
2026-08-28 (first draft assumed 768, a chip meant to be a small corner
badge rendered covering half the hub). If a coordinate in one of these
`redraw*Texture` methods looks tiny (e.g. `27, 32`) relative to what
you'd expect for a "768px" building sprite, that's the tell — it's
already in the small logical space, don't rescale it up.
