# Session: Native Blueprint Library + mobile controls, blueprint economy overhaul, real placement bugs fixed

Started from "посмотри в папке mods мод библиотеки чертежей" (an external
shapez.io mod, `mods/BlueprintLibrary.mod.js`) and ended up porting the
feature natively into the game (not as a mod — this fork's own mod-loading
system is a stub/WIP, see the earlier research in this same conversation),
plus a full pass on the blueprint economy and two real placement bugs found
via live mobile testing on the dev server.

## Summary

**Native Blueprint Library** (new feature, gated by `reward_blueprints`):
- `src/js/profile/blueprint_library_storage.js` (new) — account-wide store,
  same `ReadWriteProxy` pattern as `achievements_storage.js`. Local copy is
  authoritative (auto-compressed for free by the existing `Storage` class);
  cloud copy is a best-effort backup — whole library compressed
  (msgpack+gzip via the existing `DefaultCompression`) + base64'd into one
  blob under a `blueprintLibrary` key in Yandex's shared 200 KB player-data
  document. Soft-capped at 150 KB (`CLOUD_BUDGET_BYTES`) — over that, the
  cloud push is silently skipped (`cloudBackupCurrent` flips false) but the
  local copy is never affected.
- `src/js/game/hud/parts/blueprint_library.js` (new) — HUD dialog: search,
  tag filter chips, cards (name/tags/building count/cost/locked-buildings
  warning), Equip/Edit/Delete. Reuses `Blueprint.fromUids`/`serializeEntities`
  (new methods on `Blueprint`, `blueprint.ts`) for save, and
  `Blueprint.fromSerializedEntities` (new, backed by a `serializer_internal.js`
  refactor — extracted `buildEntityFromSerialized` so blueprint entities can
  be rebuilt *without* registering them on the map/entityMgr, same as
  `fromUids`'s clones) for equip. No import/export-by-string and no
  interactive preview canvas — deliberately cut from v1 (equip-then-undo
  already covers "preview").
- Desktop: `L` toggles the library, `K` saves the current mass-selection to
  it (`KEYMAPPINGS.ingame.menuOpenBlueprintLibrary` /
  `KEYMAPPINGS.massSelect.saveSelectionToLibrary`). 6th button added to
  `game_menu.js`/`game_menu.scss` (grid bumped 5→6 columns).
- Mobile: new "save to library" button next to `.copy` in
  `mobile_controls.js`'s `.selectPanel`; equipping arms the blueprint via the
  same `blueprintPlacer.currentBlueprint` + a new
  `HUDMobileControls.enterCopiedBlueprintMode()` (refactored out of
  `onCopyClicked`) so it enters the existing finger-follow +
  confirm/rotate/cancel row.
- Wired into `application.js`/`preload.js`/`hud_parts.ts`/`regular.js` the
  same way `wallet`/`achievements` already are.

## Blueprint economy overhaul (user-directed mid-session)

Shop already opened at level 9 (`reward_research`) but its own hint never
mentioned it (only talked about the Research/Upgrades tab). Fixed, and
restructured blueprint unlocking:
- **Level 9 hint** (`reward_research`): now also explains the Shop, buying
  upgrades, exchanging shapes↔currency, names the currency shape ("green
  circle"), and that it also spawns as map deposits.
- **Level 12**: no longer grants `reward_blueprints` — plain `no_reward` now.
- **Level 13** (`levels.js`): new reward id `reward_blueprints_shop_unlock`
  (`tutorial_goals.js`/`tutorial_goals_mappings.js`) + new `currencyBonus`
  field on `LevelDefinition`, credited to `app.wallet` in
  `hub_goals.js#onGoalCompleted` (`computeNextGoal` now threads it through
  too) — grants 1000 currency, hint points at the Shop.
- **Blueprints are now a Shop purchase**: `regular.js#generateShopItems()`
  gained a `blueprints` item (3000 currency) plus a new general-purpose
  `minLevel` field on `ShopItemDefinition`, enforced in
  `hub_goals.js#canPurchaseShopItem`. `currency_shop.js` renders a
  "Unlocks at level N" locked state (new `.levelLocked` class/CSS) instead of
  a price when `minLevel` isn't met yet.
- `T.dialogs.blueprintsNotUnlocked` (shown when trying to copy/save before
  unlock) rewritten to point at the Shop instead of "finish level 12".

## Real bugs found and fixed along the way

1. **Blueprints could never actually be placed, at all.** `Blueprint.canAfford`/
   `tryPlace` (`blueprint.ts`) paid via `hubGoals.getShapesStoredByKey`/
   `takeShapeByKey` — but the blueprint-cost shape *is* the Shop's currency
   shape, and currency shapes are explicitly documented in
   `hub_goals.js#handleDefinitionDelivered` as never entering `storedShapes`
   (they credit the wallet directly). `canAfford` was therefore always
   `false` regardless of balance. Switched both to `app.wallet.canSpend`/
   `debit`. Found while re-deriving the economy change, not reported by the
   user first — worth independent verification given no automated test
   covers it.
2. **`blueprint100k`/`blueprint1m` achievements: same root cause**
   (`achievement_tracker.js`), same fix direction — swapped to
   `hubGoals.getCurrencyAmount()` (matches `richBuratino` right next to it).
   Also reworded their descriptions (en/ru) from "have N blueprints stored"
   to "have N currency", since the two are now literally the same shape and
   the old wording was actively misleading. User confirmed "да, почини" after
   this was flagged.
3. **Overview-zoom instant-placement (desktop)**: regular buildings already
   refuse to place while zoomed into map overview unless the "remote
   building" Shop item is bought (`OverviewBuildingPolicy`) — `blueprint_placer.js`
   had no such check at all, so a blueprint placed (and charged) on a plain
   click at any zoom level. Added the same `getIsMapOverlayActive() &&
   !overviewBuildingPolicy.isAllowed()` guard to both the placement click and
   the ghost `draw()`.
4. **Mobile: blueprint placed instantly under the first finger of a
   two-finger pinch/pan, even with remote building purchased** (user-found,
   live-tested). Root cause: `HUDMobileControls.onMouseDown`'s own overview
   gate falls through (plain `return`, not `STOP_PROPAGATION`) whenever no
   regular `metaBuilding` is selected — which is *always* true while a
   blueprint (not a building) is armed — letting the touch-down reach
   `HUDBlueprintPlacer.onMouseDown` next, which then placed immediately since
   its (correct, for desktop) overview check passed. Real fix:
   `HUDBlueprintPlacer.onMouseDown`/`draw()` now no-op entirely on
   `IS_MOBILE` — mobile owns 100% of blueprint placement through
   `HUDMobileControls`'s finger-follow + explicit confirm button, the same
   way it already owns regular (non-belt) building placement; desktop's
   click-to-place logic has no business running there regardless of which
   exact touch sequence triggers it.

## Blueprint Library dialog: mobile CSS, three live-tested iterations

All found by the user testing on a real phone over Tailscale, each fixed and
redeployed within the same dev-server session:
1. Mobile grid overlap (`.info` spanning 2 rows while `.cost` also claimed
   row 2 → cost text rendered on top of building-count text) + action buttons
   overflowing horizontally (no wrap) → explicit per-row grid placement +
   `flex-wrap` on `.actions`.
2. Card/search/tag-chip backgrounds nearly invisible — lightening
   `$mainBgColor` for their fill landed almost exactly on the new warm-paper
   dialog gradient's own lightness (rebrand-era regression, not something
   specific to this file — `shape_exchange.scss` has at least one of the same
   `+8%` idiom, left alone, out of scope). First pass: flipped to transparent
   + a thin outline.
2. **Root cause of "still looks smaller/plainer than the native Edit
   dialog"**: `dialogs.scss`'s shared `.dialogInner > .content input` rule
   (big padding, soft gradient, `Text`-sized) already applied to this
   dialog's own search box by DOM structure — but this file's *own*, more
   specific (`#id .toolbar .search`) rule was silently winning the cascade
   and replacing it with a smaller, plainer one. Deleted the competing rule
   entirely (inherits the shared style for free) and hand-matched the same
   gradient/border recipe on `.blueprintCard`, switched card text to the
   same `Text`/`PlainText` mixins used everywhere else instead of ad-hoc rem
   values (also dropped the now-redundant mobile-only font-size overrides —
   the shared mixins already respond to the game's own UI-scale setting).
