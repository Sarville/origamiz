# Session 2026-08-26 — Origamiz visual rebrand, pilot batch (10 buildings)

## Context

Continuation of the asset-rebranding effort (see `REBRANDING_PLAN.md`,
project memory `yandex_games_port.md`). Working name for the rebrand:
**Origamiz** (chosen this session — wordplay on "shapez", origami theme).
This session's brief: reskin the first ~10 buildings and the toolbar in a
Japanese/origami style (paper, wood, bamboo), generate a matching toolbar,
and preview a mocked-up scene — then iterate live with the user on style
until it holds up under close inspection.

This was a single long, iterative session — the plan below is the *distilled
end state*, not a blow-by-blow (the git history / this file doesn't capture
~20 codex generation rounds). Read the "Pitfalls" section before touching
this asset line again — most of it is hard-won and will save real time.

   basket / torii gates composited on top unchanged.

   against real game source, see Pitfalls), each hut got a different bold
   silhouette treatment instead of a uniform corner-cut:
   - `cutter` — 80×80px diagonal chamfer, bottom-right (its one truly free
     corner — input bottom-left, both outputs on top).
   - `rotator` — symmetric ~30px concave "hourglass pinch" on both free
     side edges (left/right; in/out are top/bottom).
   - `stacker` — 3-step staircase notch, top-right (its one free corner).
   - `painter` — 2 large clean torn-paper notches along the fully-free
     bottom edge (a first attempt with 4-5 small zigzags read as "messy" —
     simplified per feedback).
   - `balancer` — **deliberately untouched**, plain rectangle: all 4 sides
     carry a belt connection, so "no free side" *is* its shape language.
3. **Openings** — cut by code, not drawn by the AI (see Pitfalls #1/#8).
   Exact width = the belt's own inner lane (145px), not the belt+curb
   width — the building's own curb is meant to visually continue the
   belt's curb line, not duplicate it.
4. **Roof** — building-specific folded-paper shape, unchanged from earlier
   approved passes.
5. **Plaque + icon** — one shared bamboo plaque template
   (`ui/plaque_template.png`) composited via code at a fixed size/position,
   never AI-drawn per-building (AI kept forgetting it entirely or using a
   different icon) — the icon on it is the *exact same file* as the
   toolbar icon (guarantees 1:1 match, per user's explicit ask).
6. **Arrows** — one shared arrow glyph (`ui/arrow.png`, built with PIL, not
   AI — a functional triangle doesn't need a diffusion model) composited by
   code at exact per-building coordinates derived from real game I/O data.

## Scripts (all in `assets_wip/origamiz_pilot/`, all standalone/rerunnable)

Pipeline order for touching a single building after any AI regen:
```
despill.py <file>                    # green-spill fix — NEVER on tunnel files, see Pitfalls #3
clean_corner_checkerboard.py <files> # kills the near-white fringe artifact
fill_corners.py                      # squares off the 4 true corners (has a skip-list for intentional chamfers, edit PLAN dict)
# back up here before cutting — cp buildings/X.png ref_crops/cleanN_X.png
cut_openings.py                      # cuts exact 145px belt-matching openings (edit CUTS dict for new files)
apply_arrows.py                      # composites the shared arrow at exact coords (edit JOBS dict)
apply_plaques.py                     # composites the shared plaque+matching icon (edit JOBS list)
compose_scene.py                     # rebuild the whole demo scene
```
Other one-offs: `apply_platforms.py` (composite miner/trash/tunnel content
onto a platform template), `make_arrow.py`/`make_schematics.py` (regenerate
the shared arrow / the I/O geometry diagrams used as AI references),
`qa_belt_join.py` (synthetic belt-adjacency test — **the real scene crop is
more trustworthy**, its own flat canvas background is misleading, see
Pitfalls #14), `fix_despill_damage.py` (recovery tool, see Pitfall #3),
`recolor_torii.py` / `chamfer_corners.py` / `build_corner.py` (superseded,
kept for reference only).

## Pitfalls hit this session (read before repeating any of this)

1. **Diffusion models can't be trusted for pixel-precise geometry.**
   Verify everything by measuring the actual alpha channel (numpy), never
   by eyeballing a thumbnail or trusting the model's own "verified!" self-
   report — it self-reported success on wrong-width openings, wrong-corner
   chamfers, and missing tunnel openings multiple times.
2. **AI-baked checkerboard/fringe artifact.** Near-white, *partially*
   transparent pixels (alpha 10–240, r/g/b>235) sometimes get baked into
   "transparent" regions — looks like a transparency-preview checkerboard
   that leaked into real pixel data. Scan for it explicitly
   (`clean_corner_checkerboard.py`'s technique); it does not show up in a
   simple "is alpha 0" check.
3. **`despill.py` is destructive to intentionally-green content.** It
   suppresses the green channel to fix AI chroma-key fringe — but the torii
   gates (`underground_belt_entry/exit.png`) are *supposed* to be green
   (recolored from red per user request). Ran it on those by habit twice;
   both times recovered losslessly with `fix_despill_damage.py` (R/B
   channels survive the clamp, so the original green is algebraically
   reconstructible from the HSV formula for hue=95°) — but the fix is to
   just never run `despill.py` on tunnel files, full stop.
4. **`PIL.Image.rotate()` sign errors, twice.** Positive angle = CCW. Got
   direction backwards once for "which way is up" on a belt tile, and again
   after refactoring `place_belt()`'s internal negation without updating
   the call sites (rotate=90 silently started meaning the opposite of what
   it meant before the refactor). Lesson: after ANY change to a rotation
   helper's internal sign convention, re-verify empirically (render a lone
   test tile, look at it) — don't re-derive the math in your head.
5. **A directional sprite (like a belt corner) has fixed handedness.**
   Rotating it reaches only 4 of 8 possible turn configs; the other 4
   (opposite handedness) need a horizontal/vertical flip *first*, then
   rotation. Same logic will apply to any future asset with an inherent
   left/right-turn shape.
6. **Belt corners should never have been hand/AI-drawn at all.**
   `REBRANDING_PLAN.md` §4 already says this: belts (straight + turn) are
   procedurally generated by `generate_belt_sprites.js`, same code path for
   both directions — reskin via its color/pattern constants only. Four
   rounds of AI-drawn corner pieces never quite matched the straight piece
   (border weight, lane width off by 2×) before switching to "just use the
   generator, it was right there the whole time."
7. **`node-canvas` setup, for next time:** needs system packages
   (`libpango1.0-dev libjpeg-dev libgif-dev librsvg2-dev build-essential`,
   installed this session, safe to assume present now) AND
   **`canvas@latest`, not the `^2.6.1` pinned in `package.json`** — 2.6.1's
   native build is incompatible with Node 24's V8 API; latest uses a
   prebuilt binary and just works. `cd res_raw/sprites/belt && npm install canvas`.
8. **Belt-to-building opening width is a measured constant, not a guess.**
   First guess (166px = full belt including its own curb) was wrong — user
   caught it with a hand-drawn cross-section diagram (now saved at
   `ref_crops/user_sketch_curb_alignment.jpg`): the opening must equal the
   belt's *inner* lane only (145px, excludes the belt's own 2×10px curb),
   so the building's curb visually **continues** the belt's curb line
   instead of duplicating/covering it. `cut_openings.py`'s `BELT_WIDTH`/
   `MARGIN` constants encode the correct value now — if the belt geometry
   ever changes, re-measure (`numpy`, alpha span at the belt's own mid-row)
   rather than eyeballing.
9. **Always back up a "clean" AI output before any destructive cut.**
   `cut_openings.py` zeroes alpha in place, permanently. Twice this session
   a later width/format change meant the *only* remaining copy of a
   "closed frame" intermediate had already been cut too narrow/wide, forcing
   a full paid regeneration that a `cp buildings/X.png ref_crops/cleanN_X.png`
   one-liner would have avoided. Do this immediately after every AI
   generation round, before running any `cut_*`/`apply_*` script.
10. **"Normal" rounded-corner antialiasing reads as a bug at this scale.**
    A silhouette that doesn't quite touch a sprite's 4 true corner pixels
    (standard rounded-rect antialiasing) shows as an ugly "white corner"
    once composited over a non-white background at UI scale, even though
    nothing is technically wrong. Explicitly square off all 4 true corners
    (`fill_corners.py`) on every new building **except** wherever a corner
    intentionally carries a chamfer/notch (edit its skip-list).
11. **Shape edits go only on belt-free sides — verified against source,
    not memory.** Real input/output geometry lives in
    `src/js/game/buildings/*.js` (`ItemAcceptor`/`ItemEjector` `setSlots`
    calls: `pos` + `direction`), not in the original game's visual layout
    as remembered/eyeballed. Picked the wrong corner for cutter's chamfer
    once (top-right, which actually carries an output) before re-checking
    the real slot data and moving it to bottom-right (cutter's only
    genuinely free corner).
12. **Subtle edits don't register.** A ~25px chamfer on a 384px-wide sprite
    reads as "nothing changed" at normal viewing scale. Needs to be bold —
    roughly 70–90px, about a third of the tile — to register as an
    intentional design choice at all.
13. **Too many small notches reads as messy, not detailed.** Painter's
    first jagged-bottom attempt (4-5 small zigzag teeth) got called
    "грязный" (dirty/messy); 2 large deliberate notches read as clean
    intentional design instead. Fewer + bigger beats more + smaller for
    this kind of silhouette edit.
14. **The synthetic belt-adjacency QA canvas is misleading.** Early
    (`qa_belt_join.py`) used a flat fill color for its test canvas
    background — a genuinely-transparent, correctly-cut opening rendered
    as a visible "gap patch" against that flat color, reading as a bug that
    wasn't real. The *actual* composited scene (`compose_scene.py`'s
    output, which uses the real tiled `paper_background.png`) is the
    trustworthy check — always confirm there, the synthetic canvas is only
    useful for isolating a single seam quickly.
