# Session 2026-08-27 — Origamiz: new platform+curb construction algorithm

## Context

Continuation of the Origamiz visual rebrand (`sessions/2026-08-26-2232-session.md`
was the previous chunk — pilot batch of 10 buildings, AI-drawn hut/frame look).
This session replaced that construction approach entirely on the user's
explicit request: the AI-drawn frames were "confusing," and they gave a
precise new algorithm (with hand-drawn reference sketches, now saved at
`assets_wip/origamiz_pilot/ref_crops/user_sketch_platform_shapes.jpg` and
`user_sketch_curb_alignment.jpg`) to replace them with. This file is the
spec for that algorithm — read it before touching
`assets_wip/origamiz_pilot/build_platform.py` or `build_batch.py` again,
it captures constants and pitfalls that took several iterations (and user
corrections) to land on.

**Everything below is procedural (PIL/numpy/scipy), not AI-generated.**
Session pitfall from the prior chunk ("diffusion models can't be trusted
for pixel-precise geometry") applies even harder to curbs/platforms than
it did to belt openings — this whole layer is measurable geometry, so it's
code, full stop.

## The algorithm (per-building recipe)

Every building is built as layers, bottom to top:

1. **Platform** — a flat silhouette (rounded rect by default, corner
   radius `CORNER_R=8`; some buildings cut a chamfer/staircase/notch out
   of it for "shape variety" on their belt-free sides — see below). Fill
   `PLATFORM_FILL=(236,227,200)`, thin 2px outline `PLATFORM_OUTLINE=
   (205,182,138)`. No shadow (user explicitly cancelled the drop-shadow
   requirement from the original spec message once they saw the first
   pass — may resurface later, don't re-add without asking).
2. **Curb** — a banded "plank" ring inset `CURB_INSET=13` from the
   platform's own edge, thickness `CURB_THICK=13`. Banding is 5 flat
   bands across the plank's cross-section (dark rim → mid → light core →
   mid → dark rim, see `_band_color`/`_band_color_np`) — explicitly NOT a
   tiled wood-grain texture (first attempt used `wood_texture.png`
   tiled — user called it "полосатая каша", a striped mess; flat bands
   read as clean/deliberate instead).
3. **Belt-opening cutout** — curb removed from a rectangle at each belt
   connection (see Constants below), so the lane passes through unblocked.
4. **Flank rails** — see "The seam problem" below; this is the layer that
   makes the curb actually reach the tile's outer edge at every belt
   connection, matching the belt's own curb pixel-for-pixel.
5. **Posts** — 4-faced pyramids (light top face lit from top-left, dark
   bottom face, matching an implied top-left light source) capping every
   corner and every flank rail. See "Posts" below for exact placement
   rules — this was the layer most iterated-on this session.
6. **Plaque + icon** (or, for single-connection buildings, the old
   approved 3D content crop) — centered, unchanged from the prior
   session's pipeline.
7. **Arrows** — unchanged, reused `apply_arrows`/JOBS-style data.

## Constants (measured, don't re-derive from memory)

```
TILE = 192
SS = 4                    # supersample factor, see "Antialiasing" below
CORNER_R = 8               # platform corner fillet radius (native px)
CURB_INSET = 13             # gap from platform edge to curb's outer rim
CURB_THICK = 13              # curb plank thickness
INSET = CURB_INSET + CURB_THICK/2 = 19.5   # where EVERY post sits (see Posts)
POST_SIZE = 22
MARGIN = 24, BELT_WIDTH = 145, DEPTH = 28   # belt-opening CUTOUT geometry —
                                             # copied from cut_openings.py,
                                             # NOT the same thing as
                                             # CURB_INSET/CURB_THICK, see
                                             # "The MARGIN bug" below
FLANK_DEPTH = 28           # how far a flank rail reaches in from the tile
                            # edge (== DEPTH, coincidence, kept as a
                            # separate named constant since it means a
                            # different thing)
```

Colors:
```
DARK    = #5A3418   (curb outer rim / post bottom face)
MID     = #8F5A2C   (curb inner bands / post right face)
LIGHT   = #C9925A   (curb core / post left face)
HILITE  = #E0AE78   (post top face ONLY — brighter than curb's LIGHT)
PLATFORM_FILL    = (236,227,200)
PLATFORM_OUTLINE = (205,182,138)
```

`CURB_INSET`/`CURB_THICK` are not arbitrary — they were reverse-measured
directly off `ui/belt_straight.png`'s pixel data (solid curb band x13..25
on the left edge, x166..178 on the right, antialiased edge pixel at
x13/x178) specifically so a building's curb lands on the *exact same
columns* as the belt's curb. If belt geometry ever changes, re-measure
with a raw pixel scan (`im.getpixel`) rather than eyeballing — this is
what caught the original alignment bug this session.

## Antialiasing: everything renders at SS=4 then downsamples

`PIL.ImageDraw` has zero antialiasing on `polygon`/`line`/
`rounded_rectangle` fills. First rotator pass had a visible staircase on
the pinch curve and the pyramid post edges. Fix: build the entire
platform+curb+posts composite at 4x resolution (`SS=4`), then
`canvas.resize((w,h), Image.LANCZOS)` exactly once at the very end.
Never skip this for a new shape — a chamfer diagonal or staircase step
will alias just as badly as a curve did.

## The generic curb engine: distance transform, not per-row math

Rotator's curb (`build_platform.py::build_platform_pinched`) is a
bespoke per-row closed-form (`_pinch(y)` sine formula), because its
shape was reused verbatim from the already-approved old `rotator.png`'s
alpha channel — not worth re-deriving generically for one shape.

Everything else (`build_batch.py::build_generic`) needs to handle an
arbitrary silhouette — straight rect, diagonal chamfer (cutter), 3-step
staircase (stacker), ellipse notches (painter) — with ONE formula. The
tool for that is `scipy.ndimage.distance_transform_edt`: it gives, for
every pixel, the exact Euclidean distance to the nearest background
pixel, for *any* shape. The curb ring is then just
`(dist > CURB_INSET) & (dist <= CURB_INSET + CURB_THICK)`, and the
banding value is `t = (dist - CURB_INSET) / CURB_THICK` fed into the same
5-band function — this works identically whether the nearby boundary is
straight, diagonal, or stepped.

**Gotcha (real bug this session):** most of these silhouettes fill the
*entire* canvas — there's no transparent margin at the tile's own outer
edge (unlike rotator's pinch, which visibly cuts into its own sides).
`distance_transform_edt` only measures distance to background *within
the array* — with no background pixel anywhere near the canvas edge, it
returned huge bogus distances there instead of the real inward offset,
and the curb only rendered near actual notches/chamfers (correctly
"background" nearby), vanishing everywhere else. Fix: pad the boolean
mask with a 1px `False` border before the transform and crop it back off
after:
```python
dist = distance_transform_edt(np.pad(plat, 1, constant_values=False))[1:-1, 1:-1]
```
If curb mysteriously vanishes on a new straight-edged building, check
this first.

## The seam problem: curb must reach the tile edge at belt connections

Original user spec: curb is inset from the platform edge *in general*
("отступать немного внутрь"), which the EDT ring already does correctly
for genuinely free edges (no belt nearby) — that inset is intentional and
should stay. But right where a belt attaches, the belt's own curb runs
flush to *its* tile edge, so if the building's curb stays inset there too
there's a visible gap/step at the seam. **This only applies to the strips
immediately flanking a belt opening — not to free edges in general.**

This took three iterations to get right; read all three before touching
`_flank_patches` again:

1. **First attempt** used `MARGIN`/`BELT_WIDTH` (the belt-*opening-cutout*
   geometry) to position the flanking patch. Looked plausible but was
   *wrong* — `MARGIN=24` ≠ `CURB_INSET=13`, so the patch landed a couple
   pixels off from the belt's actual curb column. **`MARGIN`/`BELT_WIDTH`/
   `DEPTH` govern where the cutout hole is; `CURB_INSET`/`CURB_THICK`
   govern where the curb *material* is. Don't conflate them** — always
   position a curb rail using `CURB_INSET`/`CURB_THICK`, never `MARGIN`.
2. **Second bug**: banding orientation. A flank strip next to a
   top/bottom (Y-axis) belt opening is a *vertical* rail (parallel to
   the belt, same as the belt's own left/right curb) — it must be banded
   **across X** (`t` varies with x, constant down y), not across Y. First
   implementation banded across Y (like a horizontal cap), which the user
   immediately caught visually ("бортики достраиваются горизонтальными
   кусками, а должны — вертикальными"). Rule: banding axis = perpendicular
   to the belt's flow direction, i.e. the SAME axis the belt's own curb
   bands across, never the axis of the tile edge the opening sits on.
3. Current implementation (`_flank_patches`): for every `(edge, offset)`
   in `belt_edges`, compute the two rail columns at
   `offset+CURB_INSET .. offset+CURB_INSET+CURB_THICK` (and the mirrored
   pair near the far side of that tile), reaching `FLANK_DEPTH=28` in
   from the relevant tile edge, banded across the perpendicular axis.
   Verify any change here against a **demo scene with a real belt tile
   placed adjacent** (`build_demo.py`) — looking at the building alone is
   not enough, both real bugs above looked fine in isolation and only
   showed up once a belt was actually butted against the seam.

## Posts: one consistent level, placed last

Posts are 4-faced pyramids (`_draw_post`): top face `HILITE` (lightest,
implied light from top-left), left face `LIGHT`, right face `MID`, bottom
face `DARK` (darkest — matches the same top-left-light convention as
elsewhere), 2px `DARK` outline. Always drawn **last**, after the curb and
its cutouts, so nothing can ever clip a post.

**Every post — corner, mid-edge, or flank-rail — sits at the exact same
perpendicular offset from its edge: `INSET = CURB_INSET + CURB_THICK/2 =
19.5`.** This was the last bug this session: an earlier version capped a
flank rail's *far/inner* end (`FLANK_DEPTH=28`) instead of its outer end,
which put that post visibly lower than the neighboring corner post — user
caught it by eye ("должны быть на одном уровне"). If a new post placement
doesn't land on `INSET`, it's probably wrong.

Placement rules, in order:
- **True 90° corners** get an explicit post in each building's
  `post_centers` (hand-specified per building — deliberately not
  auto-derived from the silhouette polygon, keeps each spec readable).
- **Chamfer/staircase vertices** also get explicit hand-placed posts
  (inset ~`INSET` along the locally-relevant axis) — see `cutter.png`/
  `stacker.png` entries in `SPECS` for the pattern.
- **Every flank rail** (one per belt-opening flank, so 2 per opening)
  gets an automatic post at `(rail_center, INSET)` on its edge —
  `_auto_flank_posts`. No "bridge vs. dead-end" special-casing needed:
  when two openings are close together (e.g. balancer's two lanes), their
  two flank-rail posts just naturally land right next to each other,
  which is exactly the look the user asked for (see their reference
  sketch, saved inline in this conversation, not yet copied to
  `ref_crops/` — if it's needed again, ask the user to resend or check
  the harness's own upload cache for `e62453f7-image.jpg`).
- **`_merge_posts(explicit, auto, min_dist=14)`** drops any auto post
  within 14px of an explicit one, so corners never get a doubled-up post.

## Shape variety (belt-free-side silhouette cuts)

Reused/re-verified from the prior session's already-correct I/O data
(`cut_openings.py`/`apply_arrows.py` — sourced from
`src/js/game/buildings/*.js` `ItemAcceptor`/`ItemEjector` slots, not from
memory or a rough sketch):

- `cutter`: 80px right-triangle chamfer at **bottom-right** (its one
  genuinely free corner — input bottom-left, outputs top-left AND
  top-right, so top-right is NOT free despite how a quick sketch might
  suggest).
- `stacker`: 3-step staircase (25px steps) at **top-right** (output only
  top-left; both bottom slots have inputs).
- `painter`: 2 large ellipse notches (`rx=60,ry=35`) centered on the
  fully-free bottom edge — no belt touches bottom at all for painter.
- `balancer`/`miner`/`trash`/tunnel entry+exit: plain rounded rect, no
  shape variety (matches the "no free side is its shape language"
  precedent from the prior session's balancer).
