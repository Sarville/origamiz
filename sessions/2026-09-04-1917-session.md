# Session: Ad monetization (rewarded video, interstitial, sticky banner, ad-removal IAP)

Continuation of the Yandex Games port, chunk 4 (`TODO.md`). Started from a
question about Yandex's rewarded-ad limits/monetization docs, ended up
building the whole ad/IAP layer on top of the existing Shop
(`sessions/2026-09-04-1624-session.md`).

## Summary

**Researched (Yandex Games SDK docs, cited to the user with sources):**
- Rewarded video (`ysdk.adv.showRewardedVideo()`) has no platform-side rate
  limit — any cap is entirely our own. Interstitial frequency IS
  platform-throttled, but only ever fires when *our* code calls
  `showFullscreenAdv()` — Yandex never injects ads unprompted. Sticky banner
  (`showBannerAdv()`/`hideBannerAdv()`) is fully game-controlled too.
- A game's own "remove ads" IAP (`payments.getPurchases()` /
  `payments.purchase()`) is unrelated to the platform-wide "buy N days
  ad-free for Yandex's own 'yans' currency" feature visible in Yandex's own
  menu — that one is entirely Yandex-side UI/economy, nothing to build for
  it, and its SDK-level interaction with our own ad calls is undocumented.
- Conclusion acted on: our own `disable_ads` IAP is a reliable, 100%
  client-side gate (we control every ad call site), independent of Yandex's
  own platform-level ad-free feature.

**Built:**
- **Rewarded-ad currency claim** (`hub_goals.js`, `currency_shop.js`): Shop
  section next to Daily Bonus. Cooldown-based (not a daily counter — changed
  mid-session per user request), `AD_REWARD_INTERVAL_MS` = 2h,
  `AD_REWARD_AMOUNT` = 250 (raised from 50). Live countdown text
  (`formatSeconds`) while on cooldown, updates every frame the dialog is
  open. Daily Bonus itself raised 250 → 1000 (`DAILY_BONUS_AMOUNT`).
- **Ad-removal IAP** (`yandex_wrapper.js`): `initialize()` now also calls
  `ysdk.getPayments({signed:false})` + `getPurchases()`, checks for product
  id `disable_ads` (this exact string, matching what the user set up in the
  Yandex Console just now), sets `this.adsDisabled`. New Shop section
  (`createRemoveAdsSection()`) calls `payments.purchase({id:"disable_ads"})`
  — real money via Yandex, not our currency.
- **Sticky banner**: `onGameReady()` now also calls `ysdk.adv.showBannerAdv()`
  if `!adsDisabled`; `hideBannerAdv()` fires immediately on a successful
  ad-removal purchase.
- **Interstitial scheduler** (new `hud/parts/interstitial_ads.js`,
  `HUDInterstitialAds`, registered in `regular.js`'s `additionalHudParts`):
  no UI of its own, just a per-frame gate. 90s grace period after entering a
  level, then attempts at most once per 4 minutes
  (`INTERSTITIAL_COOLDOWN_SECONDS`/`INTERSTITIAL_GRACE_PERIOD_SECONDS`), and
  only when `isSafeToInterrupt()`: no blocking overlay open (covers every
  text input too, since they all live inside dialogs — confirmed via an
  Explore-agent codebase sweep, not guessed), not mid-drag placing a
  building/belt (`buildingPlacer.currentlyDragging`), not holding a
  blueprint (`blueprintPlacer.currentBlueprint`), not mid marquee-select
  (`massSelector.currentSelectionStartWorld`). `showInterstitialAd()` itself
  already no-ops if `adsDisabled` or unsupported, so the scheduler doesn't
  need to re-check that.
- **Platform wrapper base** (`wrapper.js`): default no-op/false
  implementations of everything above for non-Yandex builds, PLUS a
  **dev-only fake** gated on the existing `debug.rewardedAdsInstant` flag
  (deliberately reused, not a second flag) so both the rewarded-ad button
  AND the remove-ads button/purchase can be exercised in a plain
  `npm run serve-web` browser build with no real Yandex SDK at all.
- **Savegame migration** (`savegame.js`): version bumped **1012 → 1014**
  (not straight to 1013) — see gotcha below, this is the one real bug of
  the session and worth reading if touching this file again.

## Bug found and fixed: mid-session schema rename under an already-used version number

First pass added `HubGoals.adRewardsRemaining`/`adRewardsResetAt` under
savegame version 1013 with a migration step, confirmed working. Then, per a
user request to switch from "5 claims/day" to "cooldown every 2h", those two
fields got renamed to a single `adRewardClaimedAt` — but the version number
was left at 1013. Any save that had *already* round-tripped through a
successful load+autosave at 1013 (old field names) then failed to load
again, because `migrate()` skips a save whose version already equals
current — it never got a chance to see the renamed field. Root cause:
**never reshape savegame data under a version number that might already be
on someone's disk, even mid-development** — bump again instead. Fixed with a
1013 → 1014 step that patches `adRewardClaimedAt` in if missing, covering
saves from every point in this session's history. Confirmed fixed by the
user (no third "corrupt savegame" report after this fix).
