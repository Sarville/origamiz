## Dev server access

`npm run gulp` (default task) serves the standalone dev build via browser-sync
on port 3005. Don't hand the user a raw `http://<hostname>.<tailnet>.ts.net:3005/`
link — confirmed unreliable from at least one real phone (large transfers like
the JS bundle stall/drop, only works via a Tailscale exit node). Instead run
`tailscale serve --bg --https=<port> 3005` and give that URL — it routes
through tailscaled's own HTTPS proxy and reliably reaches devices without an
exit node. Check `tailscale serve status` first for already-used ports/URLs
(other services on this machine use this pattern too).

**Bigger gotcha: any `res_raw/**` sprite change needs a manual JS rebuild too.**
`src/js/core/atlas_definitions.js` statically imports
`../../../res_built/atlas/*.json` (the packed-atlas coordinate map) — the
bundler inlines that data into the JS bundle at build time
(`res_built_atlas_atlas0_{hq,mq,lq}_atlas.bundle.js` chunks). The dev
server's watcher chain (`res_raw/**/*.png` → `imgres.buildAtlas` →
`imgres.atlasToJson` → `imgres.atlas`) only regenerates the atlas PNG/JSON
on disk; nothing watches `res_built/atlas/*.json` to trigger
`js.standalone.dev.build`. Result: after swapping any building/belt/wire
sprite, the served atlas **texture** is fresh but the running JS bundle's
baked-in **coordinates** into that texture are stale — every sprite can
render as the wrong crop/region, looking like total breakage across all
buildings and belts at once, while the atlas PNG itself (inspect it
directly) looks perfectly fine. Confirmed and fixed for real 2026-08-28,
see `sessions/2026-08-28-0923-session.md`. **After any `res_raw/**` sprite
swap, always run, in order:** `npx gulp --cwd gulp imgres.buildAtlas`,
`imgres.atlasToJson`, `imgres.atlas`, then `js.standalone.dev.build` — then
hard-refresh the browser (a normal reload can still serve a cached bundle).

**Gotcha when swapping `res/ui/**` files:** most of that tree is a plain
static-file copy with no rebuild step, but `building_icons` (and anything
else `src/css/*.scss` references via `uiResource()`/`inline()`, e.g.
`resources.scss`'s `$buildings`/`$buildingsAndVariants` lists) gets
base64-embedded into compiled CSS at build time — the dev server's watcher
only recompiles CSS on a `.scss` change, not on a change to a PNG an
`inline()` call references. After swapping such a file, `touch
src/css/resources.scss` (or run `npx gulp --cwd gulp css.dev`) to force the
re-embed, then hard-refresh the browser. See
`sessions/2026-08-28-0109-session.md` for the full diagnosis (a real
gotcha, not a caching bug — don't re-chase it as one).

## Testing the game visually in this sandbox

Headless Chrome (`--headless --screenshot=...`) reports `document.hidden = true`,
and the game itself pauses boot/rendering when hidden — this looks like a hang
but isn't a bug. For a real visual check, use Xvfb + non-headless Chrome +
`import -window <id>` (ImageMagick) for the screenshot instead.
