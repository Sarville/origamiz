## What changed

**Item 3 — crane icon.** The game-menu "shop" icon (`src/css/ingame_hud/game_menu.scss`)
was a single zigzag `<polygon>` meant to read as an origami crane but looked like a paper
dart/airplane. Redrew the polygon points (both the idle-state brown fill and the
`hasBadge` orange-pulse fill) into a clearer bird silhouette — raised wing, long neck,
pointed beak, tail. Verified by rendering the SVG standalone with `rsvg-convert` before
wiring it in (see repo-root scratch render, not committed).

**Item 4 — pin/unpin moved into the shape info dialog.**
- `src/js/game/hud/parts/shape_viewer.js`: added a `pinButton` next to the existing
  `copyKey` button. Toggles pinned state via `root.hud.parts.pinnedShapes` directly
  (`isShapePinned`/`unpinShape`/`pinNewShape`), flips its own label between
  `T.ingame.shapeViewer.pin`/`.unpin`, and hides itself (`.hidden`) for the two
  always-pinned special shapes (current goal, blueprint) where toggling doesn't apply.
  Stays open after toggling (unlike Copy Key, which closes) so the label change is visible.
- `src/js/game/hud/parts/pinned_shapes.js`: the small unpin "X" button in the mobile
  pinned-shapes strip is no longer created when `IS_MOBILE` — unpinning now only happens
  through the dialog above. Desktop keeps its existing hover unpin button unchanged.
  Also dropped a stray `console.log("unpin", key)` noticed while in there.
- `src/css/ingame_hud/shape_viewer.scss`: `.infoArea` switched from a column to a row
  (`gap: 0.6rem`, buttons `flex: 1`) so Pin/Unpin sits beside Copy Key, matching the
  reference screenshots. Added `.hidden` and a red `.pinButton.pinned` state.
- `translations/base-en.yaml` / `base-ru.yaml`: added `ingame.shapeViewer.pin`/`.unpin`
  ("Pin"/"Unpin", "Закрепить"/"Открепить").

**Item 6 — warm theme instead of gray, primary-button color instead of blue.**
Two single-place variable changes in `src/css/variables.scss` cascade through the whole
app rather than touching every call site:
- `$mainBgColor`: `#dee1ea` (cool blue-gray) → `#e8dfc9` (warm cream, matches the
  papyrus/wood palette already established elsewhere in the Origamiz rebrand). This is
  the `html { background }` in `common.scss`, so it's the base layer under every state
  (loading, main menu, settings, in-game).
- `$colorBlueBright`: `rgb(74, 151, 223)` → `#ef9d50`, the same warm orange as the
  buildings toolbar's own `.selected` highlight (`$colorOrangeBright`). This is
  `.styledButton`'s default background (`common.scss`) — i.e. every "primary/active"
  button app-wide (main menu Import/New Game, settings category tabs, dialog confirm
  buttons, etc.) — so it retints everywhere in one place instead of a file-by-file hunt.
- A few backgrounds were hardcoded hex (not driven by the variable) and needed direct
  edits: `gulp/preloader/preloader.css` (the standalone pre-JS-boot loading screen —
  can't `@use` the SCSS build, kept in sync by hand, comment added saying so),
  `src/css/states/preload.scss` `.failureBox`, `src/css/states/main_menu.scss`
  `#state_MainMenuState`'s own `background`, and `src/css/states/settings.scss`
  `.setting` card background.
- Verified by compiling SCSS standalone (`node_modules/.bin/sass`, no errors) and by
  screenshotting the running dev server via CDP (see Verification below) — confirmed
  main menu buttons, settings category tab, and all three background layers actually
  render the new colors, not just compile.

**Item 7 — Russian loading tips: already done, no code change needed.** Checked

## Verification

Live-tested against the already-running dev server (`npm run gulp`, port 3005) via the
disposable CDP Chrome instance (port 9333), per the project's established testing
approach — **not** synthetic `dispatchEvent` calls (see memory `environment-gotchas`;
used real `Input.dispatchMouseEvent`/`Page.navigate`/`Page.captureScreenshot`).

Hit the known **stale-CSS-cache pitfall twice**, both already documented in memory,
worth restating since they recurred:
1. `gulp/preloader/preloader.css` isn't in the `gulp watch` glob (`gulp/tasks.js` only
   watches `../src/html/**` for the `html` task that inlines it) — editing it alone never
   triggers a rebuild. Had to fully kill and restart the `npm run gulp` process
   (verified no duplicate instance was left behind afterward) to get it re-inlined into
   `index.html`.
2. Even after that, one CDP test tab showed a stale `html { background }` — traced to
   creating the tab via `PUT /json/new?<url>` (which starts fetching before the
   WebSocket can attach and disable cache) rather than opening `about:blank` first,
   connecting, calling `Network.setCacheDisabled`, *then* `Page.navigate`. The build on
   disk (`build/main.css`) was correct the whole time — this was purely a test-client
   artifact from the long-lived, reused Chrome debug profile. A fresh tab opened in the
   correct order confirmed all colors are actually correct in the served app.

Also opened the actual game (clicked "Продолжить" on the existing save) and confirmed
the pinned-goal-shape info dialog opens correctly with the Copy Key button now orange;
the Pin/Unpin button correctly stays hidden for the current-goal shape (it's one of the
two always-pinned special shapes) — didn't get to test the toggle on a *regular* pinned
shape live (none available at the save's current progress), but the logic is a direct,
simple boolean check reviewed by inspection.

Did not live-verify the crane icon in-game (the shop/blueprint button isn't unlocked
this early in the test save) — verified instead by rendering the SVG standalone with
`rsvg-convert` before committing to the change.

## Next steps — remaining chunks (5, 8, 9 numbering from the user's original list)

The user's full 9-item request, chunk plan proposed and being executed one session at a
time (memory `session-workflow-chunks`):

- **Chunk 2 — Undo/redo system (item 5).** Command-based history, cap 30 entries. The

  (`mobile_controls.js` `initialize()`, `.undo`/`.redo` classes, see 2026-08-30 session) —

  tap-immediately-places mobile flow with a desktop-style blueprint that follows the

- **Chunk 4 — Continuous belt placement across taps + across zoom (item 8).** Builds on
  chunk 3: once a belt segment exists, each subsequent tap should extend the belt from the
  last built tile to the new tap, surviving a zoom change in between.
- **Chunk 5 — Edit/selection mode (item 2).** New pencil-icon mode: tap-to-select
  buildings, long-press to enter the mode and select whatever's under the finger,
  drag-to-rubber-band-select an area. New center icon row while active: eraser (delete
  selected), broom (clear belt contents for any belt with a selected segment), cancel.
  Likely reuses chunk 2's undo/redo history for the eraser.
- **Chunk 6 — Auto-tunnel placement (item 9).** While laying a belt path (or on
  Ctrl-drag-release on desktop; default behavior on mobile), detect whether the new belt
  line would cross existing belts/buildings and auto-insert tunnel pairs to keep the belt
  contiguous if geometrically possible; flash the belt red on release/tap if it isn't.
  Most self-contained algorithmically, but depends on chunk 3's rewritten placement flow
  being in place first.
