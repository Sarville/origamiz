# Session 2026-08-28 09:23 — Diagnosed and fixed "everything looks broken" bug report

## Summary

User reported (via a phone screenshot over the `tailscale serve` link) that
after the previous session's asset wiring, buildings and belts all looked
wrong, and the hub only had a curb visible on the bottom and left edges.
User asked to check scripts/sizes and whether atlases needed regenerating.

## Investigation

1. Checked all 48 building file dimensions/RGBA mode against
   `REBRANDING_PLAN.md` §2.1 — all correct (already verified in the prior
   session, re-verified here).
2. Opened `build/res/atlas0_hq.png` and `atlas0_mq.png` directly (the actual
   packed textures served to clients) — both fully intact, every sprite
   individually correct, no packing corruption.
3. Reproduced on desktop (Xvfb + Chrome, same `localhost:3005` the
   `tailscale serve :8721` link proxies to, confirmed via
   `tailscale serve status`) — desktop looked correct at first, which
   initially seemed to contradict the report.
4. Root cause found: `src/js/core/atlas_definitions.js` statically imports
   `res_built/atlas/*.json` (the atlas coordinate map), and the bundler
   inlines it into the JS bundle as separate chunks
   (`res_built_atlas_atlas0_{hq,mq,lq}_atlas.bundle.js`). The dev server's
   file-watcher chain regenerates the atlas **PNG** on any `res_raw/**`
   change, but nothing watches `res_built/atlas/*.json` to trigger a JS
   rebuild (`gulp.watch("../src/js/**", ...)` only fires on JS *source*
   changes). So the previous session's building/blueprint copy refreshed
   the atlas texture but left the JS bundle's baked-in sprite coordinates
   pointing at the *old* packing layout — every building could render as
   the wrong crop of the atlas. Confirmed by checking chunk mtimes: the
   atlas bundle chunks hadn't been rebuilt since 2026-08-24/25, well before
   yesterday's asset swap.
5. Forced a full manual resync: `imgres.buildAtlas` → `imgres.atlasToJson`
   → `imgres.atlas` → `js.standalone.dev.build` (the JS variant tied to the
   running dev server, confirmed via `gulp/tasks.js`'s default task =
   `serve.standalone`). Verified via hard-refreshed screenshots: extractor
   (miner) now renders pixel-matching its source PNG (previously showed an
   unrelated smaller sprite), hub shows curb/gates on all sides, a freshly
   placed belt renders correctly connected.

## Fix applied

Ran, from `gulp/`: `npx gulp imgres.buildAtlas`, `imgres.atlasToJson`,
`imgres.atlas`, `js.standalone.dev.build`. No source files changed — this
was a stale-build issue, not a code or asset bug.
