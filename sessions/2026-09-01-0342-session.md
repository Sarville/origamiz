Continuation of the long-running chunked session on item 9/Chunk 2c. This

## What shipped this session

**Debt #3 — opportunistic connection to a nearby building's input/output**
(`belt_path_planner.js`). Added `nearbyAcceptorDirection`/`nearbyEjectorDirection`,
scanning a tile's four neighbours with the existing `buildingAcceptorFeeds`/
`buildingEjectorLaunch` (previously only ever checked the tile a drag/tap
explicitly targeted). `findBeltPath` now threads the result through as
`forcedEndOutgoing`/`forcedStartIncoming` for either end whenever it isn't
already an explicit belt/tunnel/building target. Verified live via CDP
(desktop, real mouse dispatch): a plain belt drag arriving perpendicular to
a cutter's acceptor now curves in, instead of continuing straight past it.

**Two real bugs found and fixed while verifying #3 on mobile:**
1. `buildingEjectorLaunch` only resolves a *single*-slot ejector (an
   explicit start off a multi-output building has no unambiguous "the"
   output) - but the new neighbour-lookup reused it, so a multi-output
   building (the quad cutter) never got opportunistically connected on its
   output side at all. Fixed by splitting out `buildingEjectorLaunches`
   (plural, all slots, mirrors `buildingAcceptorFeeds`'s existing
   no-restriction design); `buildingEjectorLaunch` now just filters it to
   the single-slot case.
2. `HUDMobileControls.placeSingle` (item 8's very first tap of a new belt
   chain) hardcoded `lastBeltIncomingDirection = undefined`, assuming a
   fresh tile has no real predecessor to curve from - true only when the
   ordinary engine auto-rotation hadn't already curved that first tile
   toward a neighbour. A second tap extending the chain re-derives the
   first tile's curve from that cached value, so `undefined` flattened an
   already-correct curve back to a straight line, silently disconnecting it
   - exactly a screenshot the user sent (a cutter's output flattened after
   a second tap). Fixed by reading the real rotation back off the
   just-placed tile instead (a belt's own rotation always equals its true
   incoming direction, curved or not).

Both verified live via CDP with Android UA + real touch/mouse dispatch on
an actual quad cutter.

**Debt #2 — cascading reshape without breaking existing chains**
(`belt_path_planner.js`). User showed a real screenshot: tapping into a
loop's enclosed interior left a short powerless stub cutting into the
loop's own wall, splitting off a chunk of the loop into a disconnected dead
path. Root-caused via direct CDP reproduction + `BeltSystem.beltPaths`
inspection: `isTileBlockedForBelt` already waves a same-direction existing
belt tile through as harmless reuse, but nothing stopped the search from
then *bending* at that reused tile onto a new outgoing, silently
disconnecting whatever it used to feed (the base game's own
`deleteEntityOnPathSplitIntoTwo` then correctly splits off the now-orphaned
remainder - not a corruption bug, just something the search shouldn't have
triggered). Fixed with a new `forcedExitDirection` tracked per search node
(generalizing the existing tunnel-receiver `mustContinueStraight` guard),
forcing such a node's next step to the tile's own real existing outgoing
(via a new `existingBeltOutgoing`, algebraic inverse of `curvedEntry`'s
math) - and narrowed the anchor tile's own blocking exemption from a
radius-1 neighbourhood down to the anchor tile itself, since the wider
radius turned out to be a second copy of the same loophole one tile over.

Explicitly scoped with the user: a drag/tap whose *own* endpoint
deliberately lands on an existing chain may still strand whatever fed that
exact tile before (single-acceptor belts can't do otherwise) - confirmed
acceptable, left as-is. Verified live via CDP: reproduced the original bug
first (confirmed the hijack + split), then confirmed the fix closes it
(clean detour or correct "no route" refusal, loop provably 100% unchanged),
then re-ran every earlier regression check (opportunistic acceptor/ejector,
tap-continuation curve preservation, plain open-space L-bend, deliberate
drag-onto-existing-chain merge) - all unchanged.

**New feature — mobile building placement while zoomed out into map
overview** (new `hud/parts/overview_building.js`, `mobile_controls.js`,
`building_placer_logic.js`). User request, building on top of item 8's own
stated design goal. New `OverviewBuildingPolicy.isAllowed()` - a single
decision point, unconditionally `true` for now, explicitly meant as the
seam for the monetization idea below. Three independent, previously
uncoordinated `getIsMapOverlayActive()` guards all needed relaxing behind
it: `HUDMobileControls.onMouseDown`'s entry guard, `tryPlaceCurrentBuildingAt`
itself (also reachable from a blueprint's confirm button), and
`HUDBuildingPlacerLogic.update()`'s per-tick "deselect while in overview"
housekeeping (found second, via a selection surviving one `ev()`
round-trip but not a slightly slower one). All three gated by `IS_MOBILE` -
desktop's own separate mouse handlers keep their unconditional overview
blocks, completely untouched. Verified live via CDP: belt tap-continuation
now lays a full multi-tile auto-route while zoomed out (31 tiles across two
taps); a miner's blueprint can be positioned by tap while zoomed out and
placed for real after zooming back in to confirm. Desktop regression-
checked twice (deselect-on-overview and click-does-nothing both unchanged).

**Immediate follow-up, same feature:** the map-overview waypoints hint box
