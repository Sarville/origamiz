  (white → `$dialogBgColor`) instead of per-dialog, capped width so
  nothing overflows a phone screen, hid the `kbd` (ESC/⏎) keyboard hints on
  buttons under `html.is-mobile`.
- **Root cause of "background still gray"/"no rounding at the bottom of
  settings, scroll runs to the raw edge"/"upgrades dialog cut off top and
  bottom":** `100vh` on mobile Chrome is the height with the address bar
  collapsed — taller than what's actually visible. A box sized off it
  (`.gameState.textualState`, `.ingameDialog > .dialogInner`) sticks out
  past the real bottom, or gets clipped on both ends when centered — which
  is exactly what those symptoms look like in a screenshot. Fixed
  everywhere by adding a `100dvh` declaration alongside the existing
  `100vh` one (no fallback logic needed — a browser without `dvh` support
  just keeps using the line above). Settings' own background was also made
  explicit (`background: $mainBgColor !important` + a
  `DarkThemeOverride` counterpart) instead of trusting inheritance, the
  same belt-and-braces approach the main menu's own background already
  used.
- **Statistics dialog** (`statistics.scss`): the 3 data-source tabs
  (Производится/Доставляется/Хранится) sized to their own text and
  overflowed the dialog, clipping the last one — made them an equal-width
  segmented row (`flex: 1 1 0`) instead. Recolored the dark `#44484a`
  active-tab background and the gray row-card backgrounds.
- **Upgrades/shop dialog** (`shop.scss`): recolored the remaining gray
  `.upgrade` card backgrounds, `.amount` progress badges, and the disabled
  (`:not(.buyable)`) gray "УЛУЧШИТЬ" button. Explicitly told by the user

  canvas-drawn, not CSS, so left untouched.
- **Scrollbars** (`common.scss`): found a pre-existing global
  `::-webkit-scrollbar*` rule (plain gray, `#cdd0d4`) and recolored it in
  place rather than adding a competing rule elsewhere. Added
  `scrollbar-color`/`scrollbar-width` alongside for Firefox.
- **Dark theme** (`variables.scss`, `src/js/game/themes/dark.json`):
  `$darkModeGameBackground` (drives nearly every dark surface via
  `$darkModeControlsBackground`) re-derived from `$mainBgColor`'s own hue
  instead of a separate cool blue-gray hex, so light/dark read as one
  brand. `$themeColor` (checkbox/slider "active" fill) changed from
  navy-purple to the same warm brown already used for the in-game

## Part 2 — Belt routing: wrong input on a multi-input building

**Bug (user report, with screenshots):** dragging a belt toward a
balancer's input while another one was already fed could route to the
*occupied* input instead of the free one; separately, dragging toward the
farther of two inputs could route to the *nearer* one instead. Root cause:
`BeltPathPlanner.findBeltPath` tried a target building's `ItemAcceptor`
slots in whatever fixed order the component defines them, taking the first
one *any* path existed to — completely ignoring which tile the drag ended
on or which side it approached from.

**Fix has two parts**, because the two balancer shapes need different
signals:

1. A multi-tile building (the ordinary 2-wide balancer) has each input
   slot living on its own distinct world tile — `to` (the tile the drag
   actually ended on) already names the intended slot unambiguously.
   `buildingAcceptorFeeds` now also returns each slot's own `slotTile`;
   `findBeltPath` prefers whichever feed's `slotTile` equals `to` before
   anything else. Full deliberate control, exactly matching the user's
   ask — end the drag on the wanted input's own tile, even a farther or
   already-fed one.
2. A single-tile building with several slots on the *same* tile (the
   compact merger/balancer variant — **discovered via live testing that
   this is actually the game's default balancer**, hotkey 2, not an edge
   case) has no tile left to disambiguate with. New optional `approachTile`
   param (the tile the drag/tap was over immediately before the current
   one) breaks the tie toward whichever slot's feed tile the belt is
   physically walking into on its last step, instead of whichever is
   closer to the drag's overall start. Both call sites already tracked
   this locally and just never threaded it through:
   `building_placer_logic.js`'s `oldPos` (desktop drag) and
   `mobile_controls.js`'s `dragPath`'s last tile (mobile drag).
   **Genuine physical limit, explained to the user rather than "fixed
   away":** you cannot select a same-tile input by approaching from the
   *other* one's side — under-the-finger only resolves what's
   geometrically true; getting the far one requires physically routing the
   drag to approach from that side.

**Separately, same session:** the search's own tie-break for *where* an
unavoidable bend lands used to just be `DIRECTIONS`' fixed enumeration
order, unrelated to where `to` actually was — a diagonal target could get
its bend right at its own doorstep instead of right off the source (user
showed both the current and the wanted shape by hand). New
`orderTowardGoal` helper sorts candidate directions by progress toward
`to` (both at the search's seed and at every expansion step), ties broken
toward turning over continuing straight — an unavoidable bend now happens
as early as possible, so the belt approaches a diagonal input in a clean
perpendicular run instead of hugging the source's column all the way up
first.
